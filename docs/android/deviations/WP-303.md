# WP-303 process container, per-connection graph and app state

Reference: `db14559b39d32322b06477c6ae676112f583db50`. Base: `main` @ `d2b01374`.
**External contribution:** prepared outside the dispatch controller, with no lease, session
or receipt. These are proposed adaptations for coordinator review. All code is under
`android/app/src/main/kotlin/com/meshcoreone/android/app/` (`container/`, `state/`,
`MeshCoreApplication.kt`) with tests in `android/app/src/test/.../app/container/`.

Merged code wired: `core:runtime` `ConnectionManager` and its role ports, `core:connectivity`
(pairing, presence, foreground service, permissions), `core:services` packages `messaging`,
`contacts`, `device`, `remote`, `diagnostics`, `rendering`, `sync`, `notifications`,
`reactions` and `simulator`, `core:data` `RoomPersistenceStore`, `core:datastore`,
`core:ui` `StatusPillState`/`UiText`, and the WP-302 `NavigationCoordinator`. Absent on main:
WP-218 `content/` (open PR #25), WP-307 `ChatTimeline`, WP-401 notification delivery and the
BLE `RuntimeLink`; each is reached through a narrow port and named below.

## A-01: shape and lifetime

`AppContainer` is the process object. It owns one `ConnectionManager`, one `AppState`, one
`SessionRegistry`, the pairing coordinator and the connected-device editor, and receives
every platform role through `AppContainerDependencies`. It never builds a radio-specific
service. `RadioSessionContainer` is the Swift `ServiceContainer`: one per runtime
generation, created by `RadioSessionContainerFactory` (the runtime `RuntimeServiceFactory`).
The runtime calls the factory only after the transport is open, the radio identity is
resolved and the device row exists, so no service can be constructed before a session, a
verified radio id and a generation token. Construction order follows the Swift init
(heard repeats, RX log, notifications, remote node, cleanup coordinator, contact, message,
channel, advertisement, polling, binary protocol, debug log, node config, snapshots,
repeater/room admin, room server, send queue, action handler).

- `DeviceService`/`SettingsService`/`RegionDiscoveryService` are created on first use, not
  in the factory. Their context requires the generation to be the *published* snapshot, and
  the runtime publishes `CONNECTED` after the factory returns (the first smoke run failed on
  exactly this: `Device not connected`). App-state wiring and sync both run after
  publication; an earlier access fails fast.
- `tearDown()` is single-flight and idempotent (it replays the first receipt). It runs
  every step under `NonCancellable`, records each failure as a typed `TeardownIssue` and
  continues: reset sync state, stop monitors, clear message handlers, cancel discovery
  monitoring, finish every event stream, clear the five notification forwarders and the
  identity-import callback, shut the send queue, close the message and polling services
  and the remote services, close the settings context, restore the process
  `DebugLogBuffer.shared`, then cancel the generation's supervisor job.
- Monitor start/stop serialize on one coroutine mutex. A second `startEventMonitoring` is a
  no-op, and a closed graph refuses to start (the Swift tri-state claimed the transition
  synchronously; a mutex gives the same exclusion and also lets a teardown wait for an
  in-flight start instead of skipping its own stop).
- Leak accounting is part of the API: `SessionRegistry.created/tornDown/outstanding`,
  `RadioSessionContainer.liveJobCount` (live coroutines under the graph's supervisor job)
  and `isTornDown`. The registry withdraws a container in its own teardown, so a late
  teardown can never clear its successor.

## A-02: truthful readiness and the resync loop

The runtime owns state publication and exposes no generation-checked "promote to ready after
resync" entry point (WP-214 wiring item 2), so the container does not write `READY`.
`RadioSessionContainer.initialSync` runs `SyncRetryController.performInitialSync`; if the
initial sync is not usable it waits for the resync loop to end and returns `Usable` only when
the loop's host reports promotion, or `Failed` when it is exhausted. The runtime then runs its
own promotion (device time, room re-authentication, `ensureListeners`, `onDeviceSynced`)
exactly once. `SessionResyncHost` therefore turns the loop's post-promotion hooks
(`syncDeviceTimeIfNeeded`, `sessionsAwaitingReauth`, `onDeviceSynced`) into no-ops and
stores the platform as the runtime already resolved it. On exhaustion the host fires the
"Sync Failed" pill, completes the outcome, and asks the runtime to disconnect with
`RESYNC_FAILED` from a separate coroutine (an inline disconnect would wait on the connect
operation that is waiting for this loop).

The consequence for a `connect()` caller is that it does not return until the sync either
produces a usable result or the loop gives up (three 2 s attempts after the initial sync),
and the published state stays `SYNCING` meanwhile. The status pill derives only from the
runtime state and UI timers, so it never shows Ready before `READY`
(`SessionReadinessTest`, `ProcessContainerTest`).

## A-03: cold-start pending sends

`hydrate()` runs `ChatSendQueueService.hydrate()` before the runtime publishes `CONNECTED`;
it subscribes to the connection transitions and enqueues every persisted `PendingSend` row.
The queue drains on the edge into `READY` (`canDrainSendQueue`), never earlier, and deletes
a row only after the send completes. Two behaviors the tests pin: a queued DM is transmitted
exactly once, and a full contact sync deletes local contacts the radio does not list, so a
pending send for a contact the radio no longer has is correctly discarded with it. A
disconnect before `READY` leaves the row durable for the next graph.

## A-04: `AppState`

`AppState` ports `AppState.swift` and its `+Lifecycle`, `+Wiring`, `+DeviceActions`,
`+ChatPrefetch` and `+NotificationHandlers` extensions as plain Kotlin. Observable counters
are `StateFlow`s, per-session collectors are children of one group job, and mutable members
are lock-confined (the Swift `@MainActor`). It is built from `AppStateDependencies`, whose
seams are:

- `AppConnectionPort`: the `ConnectionManager` surface app state drives (state, last
  connection, pairing flow flag, health checks, connect/disconnect, pairing, stale-node
  removal, connected-device edits). `ConnectionManagerAppPort` implements it over the
  runtime manager, `PairingCoordinator` and `ConnectedDeviceEditor`. The last-connection ids
  are a cache refreshed after every observer callback, because app state reads them
  synchronously.
- `AppSession`: the slice of the per-connection graph app state wires; the container
  implements it.
- `AppStatePlatform`: Live Activity, offline-map, App Intents and notification-navigation
  notifications, all defaulting to no-ops. Those collaborators belong to other work packages;
  the container binds only the debug-log flush.
- `RegionSelectionStore` and `StaleCleanupPreferences`, backed by the preference DataStore
  (A-09).

Swift members that are not WP-303 state and are not ported: location service, offline maps,
the store/theme services, onboarding and what's-new state, the CLI tool view model and the
device-menu tip. `AppStatePlaceholder.instance` is the inert stand-in (Swift
`AppState.placeholder`); the Compose `CompositionLocal` default that returns it belongs to the
UI work packages.

## A-05: foreground and background reconciliation

BLE lifecycle transitions are chained: each is a lazy job that first joins its predecessor,
so background and foreground hooks stay ordered under rapid bounces. The tail is never
cancelled by app state. `handleReturnToForeground` runs in the Swift order: yield, debug-log
flush, badge, WiFi health, the queued `appDidBecomeActive`, advertisement foreground drain,
platform hook, expired-ACK check (when `READY`), `checkSyncHealth`, missed battery
threshold and refresh loop, offline-map resume. `handleBecameActive` clears the surfaced
authentication-failure latch, resumes a deferred fresh pairing, scans if the picker was
requested, and arms a one-second fallback that reruns the return-to-foreground path when the
app is still disconnected.

`MeshCoreApplication` feeds the edges: the first started activity runs
`handleBecameActive` then `handleReturnToForeground`; the last stopped activity runs
`handleEnterBackground`. `ProcessForegroundState` (Swift `AppStateProviderImpl`) is the
activity count behind `AppStateProvider.isInForeground`. `checkSyncHealth` is a no-op: after
the exhaustion above the runtime is disconnected and its watchdog reconnects, and without a
promotion seam a second resync loop could not move the runtime to `READY`.

## A-06: message events

`MessageEventStream` is an `EventBroadcaster` (registration happens at `events()`, unregister
at collection end). `MessageEventDispatcher` subscribes to all six service streams
synchronously (`AppSession.subscribeMessageEvents`) before its consumers start, so the
connection-ready window loses no event. Consumers are children of one group job; a re-wire
cancels the group and closes the message-status subscription first. A throwing handler is
logged and the stream continues (Swift handlers cannot throw). Swift ids that were `Int`
carry `Long`, channel indexes `UByte`.

## A-07: connection UI

`ConnectionUiState` publishes one immutable snapshot flow and keeps the three timers (ready
toast 2 s, sync-failed pill 7 s, disconnected pill after 1 s) as lock-confined jobs, each
cancelled before replacement. Sync-activity end guards against double decrement; the Ready
toast shows only when the count returns to zero with success. `wireCallbacks` subscribes to
advertisement and contact events synchronously. Messages are `UiText.Resource` ids from the
generated l10n tables. `PairingError`, `DevicePairingError` and `SystemPairingSetupPrompt`
are the merged `core:connectivity` types; saved-device failures are classified through the
cause chain (`LinkFailure.AuthenticationFailed`, `BleTransportException` with
`BleError.AuthenticationFailed`, and the other-app variants). `userFacingMessage` is the
exception message (no localized mapping exists on main).

## A-08: prewarm, primer and battery

`ChatTimelinePrimer` and `ChatPrewarmRefresher` keep their logic and drive the timeline
through `PrimeTimeline` (bind a PRIME writer, open, read messages). `ChatTimeline`, its bake
and populator are WP-307; a prime-role implementation must be supplied through
`ChatPrimerFactory`. The tests use `StorePrimeTimeline` over the real coordinator writer, so
writer ownership, staleness and the refresh hook chain run for real, while baked render items
do not exist. A cancelled prime rethrows instead of continuing (Swift swallows its
`CancellationError` and lets `open` report `.cancelled`; the effect, no further writes, is
the same). The refresher's `makePrimer` hook replaces the Swift `linkPreviewCache` hook.

`BatteryMonitor` ports the thresholds (20/10/5, one notification per crossing, re-armed on
recovery, a recovered threshold does not stop the scan of lower ones), the 120 s refresh and
the 900 s overdue window. Starting again replaces (cancels) the previous bootstrap and loop;
Swift does not cancel, so a reconnect could leave two bootstrap tasks.

## A-09: platform and process roles

- Foreground service: `ConnectedDeviceHostBinding` combines the connection snapshot and the
  foreground flag into `HostingInput`, applies it through `ConnectedDeviceHostingController`,
  routes `ConnectedDeviceServiceHost.onStarted/onStartFailed/onStopped` to the controller and
  attaches the companion presence sink. Presence decisions (`PresenceReconnectPolicy`)
  reconnect the last radio, refresh associations on `AssociationsChanged`, forget a removed
  association through `PairingCoordinator.devicePairingDidRemoveDevice`, and report a revoked
  permission or a deferred unlock.
- Permissions: `PermissionRevocationGuard` compares each foreground snapshot with the last.
  A revoked `BLUETOOTH_CONNECT` closes only a live Bluetooth transport; a revoked
  `ACCESS_LOCAL_NETWORK` only a live LAN transport.
- Pairing: `PairingCoordinator` is built with `ensureBonded` (`BondingCoordinator` over
  `AndroidBondGateway`) and `PlatformBondInspector(Build.VERSION.SDK_INT, ...)`.
  `RuntimePlatformAdapter` and `RuntimePairingPort` are the WP-206 C-01 reference adapters,
  adopted into the app.
- Process stores: `DataStoreConnectionPreferences` (the runtime's last-connection
  preferences; dates as epoch milliseconds), `DataStoreRegionSelectionStore` (the backup-key
  JSON with the Foundation escaping of `/`), `DataStoreStaleCleanupPreferences` (the date
  stored as seconds since the Apple reference date) and `DataStoreDemoModeDefaults`
  (snapshot reads, writes persisted in order). `SharedPreferencesAssociationRecords` and
  `SharedPreferencesKnownEndpoints` give WP-206 C-07 process-death-surviving records.
  Region writes in `AppState` are queued and drained by one consumer so persisted values keep
  their order on any dispatcher.
- Link: `WifiRuntimeLink` is the TCP link; `AndroidRuntimeLinkFactory` refuses Bluetooth
  targets (C-06).

Expected values for the reference-date conversion and the JSON escaping come from
`swiftc` 6.3.2: `evidence/WP-303/wp303_foundation_oracle.swift.txt` and its `.out`.

## Coordinator notes

- **C-01 (manifest, one line).** `MeshCoreApplication` is not instantiated until the manifest
  names it, and `AndroidManifest.xml` is not a WP-303 write path. Add to the `<application>`
  element of `android/app/src/main/AndroidManifest.xml`:
  `android:name="com.meshcoreone.android.app.MeshCoreApplication"`.
- **C-02 (`MainActivity`).** The resumed activity must attach the companion chooser host and
  forward chooser results: `(application as MeshCoreApplication).container.await()
  .companionSetup?.setChooserHost(...)` and `onChooserResult(requestId, ...)` on API 31-32
  (WP-206 C-06). Not editable here (outside write paths).
- **C-03 (`core:services` visibility).** These members are `internal` and cannot be reached
  from `:app`, so the matching sync ports degrade and report the gap once through the log
  (`ServiceVisibilityGaps`, listed by `RadioSessionContainer.reportedGaps`):
  `ReactionService.findTargetMessage/findDMTargetMessage` (reactions never resolve their
  target, so they are consumed but not applied),
  `ReactionService.queuePendingReaction/queuePendingDMReaction` (never queued),
  `HeardRepeatsService.recordDistinctPathIfNeeded/harvestIncomingPaths` (extra incoming
  paths are not recorded; sent-echo repeats work), and `MeshCoreOpenReactionParser` (its
  reactions are processed as plain text). `DeduplicationKey`, `ChannelRXCorrelation`,
  `ReactionParser.parse/parseDM` and `MentionUtilities` are bound through their public
  twins. Making the five members public removes every degradation; the adapters are the only
  place to change. Also internal: `CommandAuditLogger`, so remote-command auditing binds
  `RemoteCommandAuditLog.NONE` (no audit lines are written).
- **C-04 (`core:runtime` seams, runtime not edited).** (a) No generation-checked
  `promoteToReadyAfterResync`; A-02 works around it. (b) No hook reading
  `shouldPauseWiFiHeartbeatProbe`; the container exposes it. (c) `allowedRepeatFrequencyRanges`
  has no setter; the settings-stream value is kept in `ConnectionManagerAppPort`. (d) No
  `onConnectionLost` when a failed connect detaches a live generation (WP-206 C-05); the
  container observes the disconnected edge and `AppState.reconcileSessionLoss()` resets the
  per-session state exactly once (`DisconnectReconciliationTest`). (e)
  `ProcessRuntimeMaintenance.initializeDevicePreferences` is a no-op: the Swift source has
  no equivalent at connect.
- **C-05 (`NavigationCoordinator`).** No API clears only `chatsSelectedRoute`. The container
  pops the Chats stack when the selected channel route is its top entry. A
  `clearChatSelection()` seam in WP-302 would be exact.
- **C-06 (BLE link).** No `RuntimeLink` over `core:ble`'s `BleTransport` is merged: mapping its
  phase diagnostics to `LinkCallbacks`, `FirmwareFrameCapabilities` from `DeviceCapabilities`
  and bond refresh is unowned. `AndroidRuntimeLinkFactory` therefore throws
  `ConnectionError.UnsupportedCapability("bluetooth runtime link")` for Bluetooth targets, and
  the `BleLinkInspector` reports an idle link. `SystemLinkAdopter` is a refusing adopter for
  the same reason. LAN binding (`LocalNetworkBinding`) is not wired into `WifiRuntimeLink`; it
  uses a default socket.
- **C-07 (other unmerged roles).** `NotificationDeliveryPort` (WP-401) is bound to
  `UnavailableNotificationDelivery`, which reports the capability unsupported;
  `NotificationStringProvider`, `AccessibilityAnnouncer`, the content/link-preview prefetcher
  (WP-218) and the `ChatTimeline` (WP-307) are not bound. Simulator mode (WP-217): the
  runtime has no simulator target, `SimulatorSeedStore` lacks two contract members, and the
  image seeder needs the WP-218 cache, so `simulatorConnect` and seeding are not wired; only
  `DemoModeDefaults` is installed.
- **C-08 (on-device validation).** The DataStore, SharedPreferences and `MeshCoreStorage`
  adapters run under Robolectric here (the Keystore-backed secret path is not exercised: the
  password vault is a port). The production factory, `MeshCoreApplication`, the foreground
  service and the companion/permission/bonding routes have no instrumented or device run.
- **C-09 (build).** `./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
  validateModuleGraph` passes with `--dependency-verification lenient` and
  `-x :core:ui:verifySharedUiInputs`; the WP-302 navigation evidence tasks pass when the
  checkout is committed (they compare compiled bytes with Git).
