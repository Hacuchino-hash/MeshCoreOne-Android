## Domain and Room boundaries

The implementation composes the actual WP-201 neutral persistence roles
over its seventeen-table Room schema 1. No parallel DTO/database adapter,
SwiftData file, destructive fallback or schema 2 is introduced. Writes use
actual Room transactions and generated DAOs; reads use the existing
checked DTO projections. Partial mutations preserve the entity's original
unmodified columns, rather than passing through creation-only defaults
that normalize timestamp-zero, preview blobs or legacy date/enum fields.

Child APIs take `(radioId, id)` keys, including pending-send message
lookups. This is the approved WP-201 identity adaptation: equal IDs on two
radios cannot cross partitions. Stored/restored radio identity is not
recomputed from a connection handle. Registry ghost reconciliation adopts
the ghost's radio ID and leaves temporary post-pair children in their
original partition, as the pinned source does.

Contact public-key/name hints deliberately search all radios. Debug logs
and URL preview cache are process-global; node history is shared by full
remote-node public key. Device-data deletion uses the actual global
session-reference guard before deleting shared history. Room-message and
repeat orphans are not promoted into invented automatic cascades. Single
message removal uses only the existing linked-repeat FK cascade; bulk
contact/channel/radio operations explicitly remove the source's dependent
repeat/pending/reaction rows.

## Serialization, cancellation and diagnostic batches

A per-store mutex protects complete operations across DAO suspensions,
including allocation of per-radio pending sequence numbers and atomic
snapshot enrichment. Room transactions supply rollback and consistent
multi-query snapshots. Cancellation is rethrown; failed operations do not
replace a database or return an empty successful collection.

RX inserts retain the source's twenty-insert batch and one-second partial
flush. Store reads overlay immutable pending rows so a lookup can see an
insert before its batch commit. Ordinary successful source saves
piggyback those inserts. Source rollback-sensitive contact/channel
cascades flush the prior diagnostic batch separately before attempting
their own transaction. Buffer/cache bookkeeping and inbound-hop consumption
occur only after successful transaction completion. The process owner
injects the coroutine scope and clock; repository close flushes and stops
its own jobs/observations but does not close the externally owned database.
No connection teardown is wired to destroy this process store.

Room can commit on its transaction executor and then observe caller
cancellation before returning to the caller dispatcher. A bounded,
function-owned transaction job forwards cancellation while mutations are
still staged, then protects only the final commit and non-suspending
in-memory buffer/cache completion. The original caller's cancellation is
rechecked and rethrown afterward. It does not make an entire operation
non-cancellable or report a committed deletion as rolled back. A genuine
Room transaction-executor regression cancels exactly on that return edge
and checks a later diagnostic flush cannot resurrect the deleted row.

Unsupported pending-send kinds retain the source's explicit
report-and-filter behavior without deleting the raw row. Other malformed
checked projections surface `PersistenceStoreException` with the actual
`DatabaseValueException` or SQLite cause, following WP-201's reviewed
corruption adaptation rather than the source's success-shaped corrupt-row
defaults. Logs report operation/error kinds without identifiers, payloads
or credentials.

Reaction matching uses the real text-plus-little-endian-UInt32 SHA-256
five-byte/Crockford hash, not the content-dedup hash. Orphan adoption and
DM matching recognize the pinned PocketMesh and meshcore-open formats.
The narrow reaction-emoji predicate uses Android ICU grapheme boundaries
and its emoji property for the same first-scalar rule. Runtime Unicode
version differences are a native platform boundary, not an assertion of
all later WP-216 parser/UI parity.

## Initial schema and historical Apple migration cases

The five source migration suites contain eighteen historical SwiftData/
UserDefaults declarations. Their old BLE-column rename, one-time Apple
preference guards and interim SwiftData sort-date/flood-scope sweeps are
not silently copied into Android schema numbering or ordinary warm-up.
Native schema 1 already has distinct stable radio IDs, explicit sort dates,
raw flood-scope storage and the correct badge filters.

These eighteen declarations now have individual coordinator-reviewed
native-equivalent/Apple-historical-only-exclusion code adaptations. They
are not counted as passed by a header or by the initial schema's existence.
Full compatible
backup decoding, legacy field repair, restore remapping and preference
completion remain WP-203/204; this package does not claim those oracles.
The case-specific [proposal](../evidence/WP-202/migration-dispositions.json)
names all eighteen original IDs/blobs, each original mutation or guard,
an actual authored `InitialSchemaMigrationBoundaryTest` assertion and any
retained downstream consumer. Unknown/explicit channel raw modes, existing
dedup keys, restored radio IDs and explicit sync sort dates are deliberately
not rewritten by ordinary v1 warm-up. No blanket migration-case exclusion has been accepted or represented as
native execution. The exact original date/text/repeater parameters and
independently sourced `Date.distantPast`/hex-letter UUID/UTF-8 vectors are
retained alongside negative/fractional/nanosecond cases. Real raw native
assertions are still required before any execution disposition resolves.

The two unsigned-path source export cases are being translated into actual
Room file reopen plus checked `-1` to `255` projections. This is a native
row/reopen equivalent, not whole-backup export/restore proof. Windows
Robolectric's existing WAL VFS limitation is handled by **test-only**
TRUNCATE journal mode. Production retains `MeshCoreDatabase.open` and its
AUTOMATIC mode; no device/WAL certification is claimed.
