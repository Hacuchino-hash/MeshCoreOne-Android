host, preserving `com.meshcoreone.android.MainActivity`. The shell uses actual

No feature placeholder is claimed as a completed screen. The shell constructs
no repository, notification service, connection, permission request or radio.

The native icon rail is 80dp instead of the source 64-point sidebar. The source
380/320 content/detail preferences remain: three-region tiling starts at usable

native bar becomes a rail, not an assertion of three-column parity. Map has no

regular-width Tools tab exit clears its selection as in the source sidebar.
Scrollable rail and scalable bar/title layouts are implemented, not yet verified.

Private DTOs, radio IDs, keys and staged links remain memory-only. A retained
ViewModel keeps them on activity recreation; versioned process restoration saves
only public/offline routes and opaque entry IDs, redacts private detail entries
and exposes `PrivateSelectionNotRestored`. This is deliberately not a claim
that a private selected contact survives process death. Feature saveable content
must independently obey its own privacy contract.

Notification callbacks are bound to the actual existing `NotificationService`
through an explicit closeable adapter; the caller retains connection/scope
ownership. Read-only lookup delegates to the supplied process store. Generation
checks and atomic state commits reject late successes/errors, cancellation
propagates, and missing/invalid entities have typed localized recovery rather
than Swift's silent `try?`. Cold requests wait for graph readiness, are FIFO
and one-shot; cancellation before commit retains the queued request. WP-303
must perform actual graph/OS-event registration and invoke readiness/draining.

The source `ChatViewModel.navigateToMap` callback body is extracted into
`MapNavigationConsumer`, not a fabricated ChatViewModel. Its assertion exercises
that real forwarding body; unavailable sink remains an explicit no-navigation
outcome. This narrow consumer equivalent is **pending parity review**, not a
claim that the future chat feature is implemented.

The shared original cases now exercise real notification callback registration
and seeded Room lookup. All fifty original bodies and 140 local native nodes

## Historical admission findings (superseded where stated above)

The five authorized primary paths initially had a real canonical shared reservation.
However, the actual manifest launches the older
`com.meshcoreone.android.MainActivity`, outside those paths. There are no
declared Navigation3/Material adaptive dependencies or instrumentation-test
runner wiring, and the official App verification task only runs unit tests.
Implementing an unreachable Activity, relabeling scaffold navigation as Nav3 or
adding undiscovered tests would not satisfy WP-302.

The concrete six-path support proposal is
[`support-path-amendment.json`](../evidence/WP-302/support-path-amendment.json).
App build, App lock and root checksum metadata overlap D0/WP-218's active
reservation. Approval alone cannot override that lease; coordinated exclusive
ownership or an authorized producer handoff is required.

Proposed native adaptation: retain the current externally visible launcher
identity with a thin bridge into the authorized app Activity. This avoids an
unnecessary manifest/shared APK-inspector amendment. Preserve five source tab
indices, Material theme tokens, existing feature entry boundaries and the sole
process/radio owner. This was initially a proposal; the three nonoverlapping paths are now approved,
leased and implemented. App build/lock/checksum remain solely D0.

Source selected-contact state is memory-only and must not be serialized as a
DTO/public key/radio ID when implementing saved navigation. Source layout
constants, tool-specific sidebar collapse and offline/per-device selection
lifetimes need explicit native assertions; generic responsive scaffold tests
and WP-304's source evidence do not prove those behaviors.
