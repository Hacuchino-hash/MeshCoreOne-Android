# WP-401 Messaging notification delivery

Reference: `db14559b39d32322b06477c6ae676112f583db50`. Owner: `platform-integrations-engineer`.
External contribution, no lease. No device, emulator or Robolectric verification is claimed.

## What is delivered (`platform/notifications/.../messaging/`)

| Swift (`UNUserNotificationCenter`) | Android adapter |
| --- | --- |
| `NotificationCategory` / actions | `MessagingNotificationDelivery.registerCategories` + `MessagingChannels` (five channels plus a low-importance silent twin of each; Android fixes sound per channel, so "no sound" selects the twin) |
| Banner with thread identifier | `MessagingNotificationFactory`: `Notification.MessagingStyle` for direct/channel/room messages, group key = thread id, conversation shortcut (`ConversationShortcuts`, long-lived dynamic shortcut + shortcut id) |
| Reply (text input) / Mark as Read | Notification actions with `RemoteInput`; PendingIntents are explicit-component. Only the reply PendingIntent is `FLAG_MUTABLE` (RemoteInput requirement); mark-read and content tap are `FLAG_IMMUTABLE` |
| `userInfo` | `NotificationPayloadCodec`: strict string encoding (every id carries its radio, no regex, malformed input decodes to null) stored in notification extras and PendingIntent extras so it survives process death |
| `didReceive` entry | `MessagingActionReceiver` -> `MessagingResponseRouter` -> app-installed `NotificationResponseSink` (normally `NotificationService.didReceive`) |
| authorization | `MessagingAuthorization` + app-owned `NotificationPermissionGateway`; denial returns `NotificationPostResult.PermissionDenied`, never throws into messaging |
| badge count | No-op: Android has no app-set badge API; launchers count active notifications. `NotificationRequest.badge` maps to `setNumber` |

## Guards

- Cold start: the receiver may run in a fresh process before the service graph exists. The router queues
  (bounded, 16) and replays in order on `attach`. A reply is never dropped. A mark-read expires after 120 s in the
  queue. Overflow evicts mark-read first.
- Stale radio: the WP-215 `NotificationActionHandler` already refuses to transmit a reply from another radio (draft
  plus failure notification) and writes mark-read only to the action's own radio rows. The router adds only
  classification (`DELIVERED_STALE_RADIO`) and never discards text.
- Notifications never gate messaging: the adapter has no dependency on send/receive paths; every failure is a
  `PostResult` or a throw the policy contains.
- Reply spinner: after a reply is handed over, the receiver cancels the original notification so the platform
  spinner cannot stick (failure notices are posted by the policy under their own ids).

## Deviations and gaps (outside WP-401 write paths)

1. `android/platform/notifications/src/main/AndroidManifest.xml` still declares nothing. The app must add
   `POST_NOTIFICATIONS`, register a non-exported `MessagingActionReceiver` (subclass or direct) and pass its
   `ComponentName` to `MessagingNotificationDelivery` (WP-407 owns the app manifest).
2. App wiring (WP-303/407): `MessagingNotifications.router.attach(sink)` with `NotificationService::didReceive`
   after the service is built; `detach` on teardown; an Activity-backed `NotificationPermissionGateway`; localized
   `MessagingChannelLabels` (the module has no string resources); reading `EXTRA_PAYLOAD` from the launch intent
   with `MessagingNotificationFactory.payloadFrom` to route taps.
3. `android/platform/notifications/build.gradle.kts` is not writable here, so the `verifyScaffoldTests` hook is
   not wired and `androidTest` has no JUnit on its classpath. The test file
   (`MessagingNotificationTests`) is dependency-free, compile-only, and exposes `cases` for a later runner.
   `src/test` is outside the write paths (`portmap.py` rejects it). The nine cases were executed once locally by a
   temporary, uncommitted copy under `src/test` (all passed); that run is not a gate.
4. `Notification.Builder` lacks `setSilent`/`setShowsUserInterface` (compat-only); handled with silent channels
   and the framework default. No new dependency was added.
5. Foreground suppression (`shouldPresentWhileForeground`) is not implemented here: Android presents
   notifications posted by the process regardless; the policy simply should not post for the open conversation.

Source/test parity: no Swift test file maps to this layer; policy behavior tests live in WP-215. Original-case
inventory approval (WP-004) is pending, so completion is not asserted.
