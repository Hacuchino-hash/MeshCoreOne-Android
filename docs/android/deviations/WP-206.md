## A-01: AccessorySetupKit becomes CompanionDeviceManager association

The ASK session becomes a snapshot of this app's CDM associations (`getMyAssociations`
API 33+, address list API 31-32). The picker is the CDM chooser, filtered on the NUS
service through `BluetoothLeDeviceFilter`. "Filtered discovery" maps to CDM listing each
match by its advertised name. CDM needs a resumed activity to launch the chooser's
`IntentSender`. With no `CompanionChooserHost` attached, the picker fails as
`PickerRestricted`, which maps to `DevicePairingError.PickerUnavailable`. The host is
read when the chooser is launched, not when the picker starts, and an abandoned request
is never launched. API 31-32 deliver the result through the activity result, which the
host forwards to `onChooserResult(requestId, ...)`; API 33+ deliver it through
`onAssociationCreated`. Results are correlated by request id (`ChooserRequests`), so a
late result never resolves a newer request. An unowned API 31-32 selection is
disassociated as an orphan. Failure codes are typed only from API 36
(`onFailure(int, CharSequence)`); on API 31-35 the AOSP reason strings `user_rejected`
and `canceled` (dismissal) and `discovery_timeout` are matched, and anything else is a
connection failure (`CompanionFailureMapping`). An association the system creates
without a usable MAC address is disassociated before `NoBluetoothIdentifier` is reported.

CDM stores a display name only for self-managed associations. The advertised name is
therefore captured at association time and kept in an `AssociationRecordStore`. API
34+ reads it from `associatedDevice.bleDevice.scanRecord`; API 31-33 read it from the
chooser result's `ScanResult`. Recorded names replace the default label.

If the awaiting coroutine is cancelled, a later association is disassociated as an
orphan, like ASK's `pickerWasCancelled`. This is tracked per chooser request. A
pairing failure for a listed association fires `didFailPairing` and removes it.
Removals made in Settings have no callback before API 36, so they are detected when
associations are refreshed on activation or foreground and reported once through
`didRemove`. The diff baseline is the durable association record, so a removal made
while the process was dead is still reported. API 36 `EVENT_ASSOCIATION_REMOVED` for an
id that `getMyAssociations` no longer lists becomes `PresenceEvent.AssociationsChanged`,
which triggers that refresh instead of being dropped. Android has no system rename
sheet (`supportsSystemRename = false`) and no removal confirmation. The
`UserCancelled` mapping is kept for parity. Association never opens GATT, bonds, or
grants a background exemption (A-05).

## A-02: endpoint ids and rotating addresses

CoreBluetooth's per-install peripheral UUID becomes a name-based UUID of the canonical
(uppercase, `Locale.ROOT`) MAC address. It is an endpoint handle only; radio identity
remains the public-key radio id. Unbonded private addresses (top bits `01`/`00`) are
`Ephemeral`. They must be bonded, so Android resolves the identity address, before the
endpoint is relied on across sessions. Static-random and bonded addresses are
`Stable`. Scan-fallback endpoints live in `KnownEndpointStore`; only the in-memory
implementation ships here (C-07).

## A-03: explicit bonding and PIN

ASK collects the PIN inside its picker. On Android, `BondingCoordinator.ensureBonded`
calls `createBond` unless the device is already bonded or bonding, and observes
`ACTION_BOND_STATE_CHANGED`/`ACTION_PAIRING_REQUEST`. The receiver is registered
`RECEIVER_EXPORTED`: the Bluetooth app (its own uid) sends these protected broadcasts,
and a `NOT_EXPORTED` receiver would drop them on API 33+. It registers before
re-checking state and has a 60 s injected-clock timeout; at the timeout it re-reads the
bond state, so a missed broadcast cannot fail a completed bond. The system dialog collects the PIN; the
app never injects one. `PinEntry` progress is exposed for UI. Unbond reasons 1/2/6/7
are `AuthenticationFailed` (classified for guided recovery). 3/8 are `Canceled`; 4 and
9 have their own reasons. `PairingCoordinator` runs bonding between discovery and
connect when the host supplies `ensureBonded`. A bond failure becomes
`PairingError.ConnectionFailed` and the association is **not** removed, which matches
the source rule that pairing never removes associations.

Association removal (cleanup, remove-and-retry, forget, delete) also removes the system
bond on API 36+ through `CompanionDeviceManager.removeBond(associationId)` before
`disassociate`. Before API 36 the app cannot remove bonds. An authentication failure
while the platform still reports the device as bonded is then treated as a stale bond:
`PairingError.ConnectionFailed.recovery` is `ForgetInBluetoothSettings`, and the UI
routes the user to Bluetooth settings. Otherwise auth failures offer `RemoveAndRetry`
(`BondInspector`/`PlatformBondInspector`).

## A-04: permissions, capability and fallbacks

`BLUETOOTH_CONNECT` is required for connect and companion pairing. `BLUETOOTH_SCAN`
(declared `neverForLocation`) is required only for the scan fallback, because CDM
scans system-side. No location permission is declared. Location Services off is only a
non-blocking `LocationServicesOff` advisory for the fallback. `POST_NOTIFICATIONS` is
optional (API 33+; `NotificationsHidden`). `ACCESS_LOCAL_NETWORK` applies from API 37,
for LAN only. LAN denial never affects BLE. Denial produces typed
`ConnectionIssue.PermissionDenied`. A missing adapter or CDM feature produces
`Unsupported`. Bluetooth off produces `BluetoothOff`, and before first unlock the result
is `UserLocked`. Revocation is the set granted before but missing now, and a
`SecurityException` classifies as `BluetoothUnauthorized`. `NEARBY_WIFI_DEVICES` is not
needed for TCP to a LAN host and is not declared.

## A-05: one connectedDevice foreground service

`ConnectedDeviceService` is the only foreground service: `foregroundServiceType=
connectedDevice`, not exported, `START_NOT_STICKY`. It owns no GATT or socket.
`ConnectedDeviceHostingController` holds the service while the user wants a connection
and the link is live or reconnecting. It releases the service on user disconnect or
when disconnected and idle, and starts it at most once. **Only a visible app starts the
service.** A companion association or presence callback is not a platform exemption
without `REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND`. That permission,
like `REQUEST_COMPANION_RUN_IN_BACKGROUND`, is deliberately not declared, because it
would make association a blanket background exemption. Background starts are deferred to
the next foreground. A presence-driven reconnect runs while the system keeps
`MeshCompanionDeviceService` bound. Declaring the permission is a product decision for
coordinator/human review.

The service always calls `startForeground` first. Notification-provider failures fall
back to the minimal notification rather than aborting the start. The controller never
stops a service that has not reported `startForeground`: a release that arrives while
the service is starting becomes `StopPending` and is applied in `onServiceStarted`,
because stopping a `startForegroundService` service earlier crashes the app. On API 34
the type check throws inside `startForeground`. The service reports it through
`ConnectedDeviceServiceHost.onStartFailed`, which resets the hold and records
`StartOutcome.TypeNotPermitted`, and then stops itself. A
`ForegroundServiceStartNotAllowedException` from `startForegroundService` is a typed
deferral. The type
prerequisite is `BLUETOOTH_CONNECT` for BLE, or `CHANGE_NETWORK_STATE` (install-time) for
LAN-only. Notification copy belongs to WP-402 (`ConnectedDeviceNotificationProvider`).
The fallback notification uses only the app label and icon.

## A-06: presence auto-reconnect, pre-unlock and process death

iOS auto-reconnect and state restoration become CDM presence. The session observes
presence for every association: `ObservingDevicePresenceRequest` from API 36, the
address form before that. It stops before removal and never observes orphans.
`MeshCompanionDeviceService` (permission `BIND_COMPANION_DEVICE_SERVICE`) forwards
appear/disappear/removed events, with API 31/33/36 callback guards, through
`CompanionPresenceDispatcher`. If the binding started a fresh process before the host
attached its sink, the latest event per device is buffered (bounded) and replayed.
`PresenceReconnectPolicy` reconnects only the last-connected radio, and only when the
user wants a connection and it is disconnected. Before first unlock it returns
`DeferUntilUnlock`; with Bluetooth connect revoked, `PermissionRevoked`. Disappearance
is not treated as link loss (the link reports its own loss). Nothing promises reconnect
after force-stop or OEM kills.

## A-07: WiFi binding and ACCESS_LOCAL_NETWORK

`LocalNetworkBinder` requests `TRANSPORT_WIFI` with `NET_CAPABILITY_INTERNET`
removed, so a radio's own AP qualifies, with a 10 s injected-clock timeout. The
resulting `NetworkLease` builds `WiFiTransport` with the network's socket factory and
DNS (`Network.getByName`). After `onLost` it fails fast and never falls back to the
default route. Denial, unavailable, timeout and cancellation release the request.
Network-scoped DNS does not resolve `.local` mDNS names. That is a documented limit
(WP-108 resolver seam), not a fallback.

## A-08: scan-fallback service and structured cancellation

`BluetoothScanPairingService` is the analogue of the source's macOS scan picker,
selected when `FEATURE_COMPANION_DEVICE_SETUP` is missing. Presentation is a
`StateFlow`. Cancelling the awaiting coroutine surfaces Kotlin `CancellationException`,
never `DevicePairingError.Cancelled`, because cancellation is not rewritten into a
domain error. The cancellation handler runs synchronously during `cancel()`, so a
racing `select` still cannot win. Two source cases are therefore `platform-adaptation`.

## A-09: pairing flow ordering

- Connection intent becomes `wantsConnection` when the runtime's `connect` is submitted,
  not before the picker. The pairing flag defers opportunistic reconnects for the whole
  flow, as in the source.
- After `connect` returns without an operational session (the runtime's adoption path
  returns at `CONNECTING`), pairing waits for adoption to settle: 50 ms poll, 15 s
  limit, with the source detail strings.
- If cancellation lands in the other-app wait, it unwinds immediately instead of
  returning `false` first. Partial-pairing cleanup (association removal) still runs, so
  the net effect is the same.
- `removeFailedPairing` clears the persisted connection/bond **first**. On Android, bond
  verification lives on the live link generation, which the transport teardown
  discards; the source cleared a process-wide state machine last.

## A-10: connected-device edits and node maintenance

The source's updates mutate `connectedDevice` in place. The runtime exposes it
read-only, so `ConnectedDeviceEditor` works over an injected `ConnectedDeviceAccess`
(C-03), persists through `DevicePersisting`, and reports failures. The radio-preset
catalog belongs to WP-211 and is injected as `RadioPresetMatcher`. Tests use the frozen
br/us-ca/ca rows with the source tolerances. Node maintenance uses `ContactPersisting`
and a `ContactRemovalPort` for the session contact service, and keeps the V-contact
exclusion. The 11 device-update cases are `native-equivalent`.

## A-11: test architecture

Most owned cases test `ConnectionManager`, which WP-207 implemented in `core:runtime`.
They run against the **real runtime** with the merged `MeshCoreSession` over a fake radio
that answers the startup handshake frames. Platform facts flow through the production
`ConnectivityPlatform`/`BleLinkInspector`/`CompanionPairingService` and the
`MockCompanionSetupService` port of the ASK mock. Source `setTestState` seeding is
replaced by real transitions (connect, link loss, sync failure, gated radio connects).
The locked test classpath has neither `kotlinx-coroutines-test` nor Robolectric, so a
single-thread `runBlocking` scenario with a virtual `ManualClock` is used. The Android
adapter classes (`platform/*`, `ConnectedDeviceService`, `AndroidPermissionState`) are
compile- and lint-checked only (C-09). Original ids are bound with
`@OriginalCase(id, disposition)` on JUnit4 methods, as in core:data.

## A-12: source behavior already owned by core:runtime

The health ladder, watchdog, connection loss, auth-failure latch, READY promotion,
adoption/other-app ladder, WiFi heartbeat/reconnect/health and the retry/circuit
budget are WP-207 runtime code. WP-206 provides their platform inputs (link state,
registry, classification, adoption) and ports their tests. `isDeviceConnectedToOtherApp`,
`isOwnedSystemConnectedLink`, availability mapping and the diagnostics summary are
ported in `BleLinkInspector`. `bleConnectionMethods` is not ported: runtime A-03 forbids
fake Apple `.bluetooth` connection methods. Android has no OS auto-reconnect, so
`autoReconnecting` reports only an explicit owner reconnect phase. Three such cases are
`platform-adaptation`.

## Independent review follow-up (commit after b6b6fada)

1. Merged APK permission expectations were updated out of path (C-09).
2. The bond receiver is `RECEIVER_EXPORTED`, and bond state is re-read at timeout (A-03).
3. API 36+ calls `removeBond` before `disassociate`; before 36, stale-bond recovery
   routes to Bluetooth settings, and the cleanup comment is corrected (A-03).
4. `startForeground` comes first, and releases are deferred until the service has
   started (A-05).
5. Typed CDM failure codes are API 36+; AOSP reason strings are mapped on 31-35 (A-01).
6. An API 36 removal of an unknown association triggers a refresh, diffed against the
   durable record (A-01, A-06).
7. Advertised names are captured at association time and recorded (A-01).
8. The presence-callback "exemption" is dropped: background starts defer (A-05).
9. `startForeground` type failures are reported from the service and reset the hold (A-05).
10. The chooser host is read at launch time; abandoned requests are not launched (A-01).
11. Chooser results are correlated by request id (A-01).
12. An unaddressable system-created association is disassociated (A-01).

Each item has a JVM regression test except the platform-only parts of 2, 3 and 12,
which are lint/compile-checked; see "Device-only verification".

## Supervised PR #58 integration repair

Base: `372fbc5866305e045025472ba555e7941873000f`, the actual PR #58 merge.
The unmodified connectivity suite reproduced 174 discovered cases with three
failures, all stale assertions expecting an exception from the now-contained
foreground health reconnect. The pinned Swift auth-routing and BLE-health cases
await normal completion and inspect recovery/cleanup behavior instead.

The repair changes only the two source-bound connectivity test classes and
WP-206 evidence/deviations. It preserves all original-case bindings and 174 cases,
replaces the three exception assertions with typed diagnostic assertions, and
removes the health tests' catch-and-ignore helper so unexpected exceptions and
cancellation cannot masquerade as successful state checks. Runtime, platform
production code, Swift inputs and shared build/policy files are unchanged.
See [`../evidence/WP-206/integration-repair.md`](../evidence/WP-206/integration-repair.md)
for the actual verification outcomes and supervised lease binding. This repair
does not retroactively lease or formally accept the original external contribution.
