# WP-108 native transport adaptations

Reference: `db14559b39d32322b06477c6ae676112f583db50`. Owner: `protocol-porter`.
Only the explicitly authorized mock/TCP source, transport tests and WP-108
documentation/evidence paths change. Neither `MeshTransport.kt`, shared models,
dependencies, locks, workflows nor the Swift reference changes.

## Wire and capabilities

The wire remains `<` / `>` + unsigned UInt16 little-endian length + unchanged
payload. Empty frames and the full 65,535-byte payload are valid; a 65,536-byte
outbound payload throws `WiFiFrameException.PayloadTooLarge`, rather than the
Swift checked UInt16 conversion trap. No truncation, padding, protocol-code
filtering or smaller invented packet limit is applied.

The decoder retains at most a three-byte header and a 65,535-byte payload. TCP
reads retain the source's 65,536-byte maximum. A UInt16 header cannot represent
an inbound length greater than 65,535; testing a fabricated larger wire field
would be incorrect. Delimiter resynchronization matches the source, with an
observable discarded-noise counter; delimiter bytes inside payloads are data.
`finish()` additionally reports incomplete headers/payloads at unexpected EOF
instead of silently discarding a partial frame. Explicit user disconnect
discards an unfinished frame, matching teardown rather than malformed-peer EOF.

TCP advertises pipelined reads, **not** Write-Without-Response. The default
`sendWithoutResponse` still calls `send`. Mock capabilities remain opt-in, and
the inherited pipelining capability mirrors its configured write capability.
TCP disables Nagle, uses no TLS, discovery, heartbeat or automatic reconnect.

## Streams, generations and errors

The source constructs one default-unbounded `AsyncStream` at initialization.
The native mapping is one default-unbounded `Channel<Bytes>.receiveAsFlow()`
ingestion queue per connection, available before first connect. It is not a
broadcaster, StateFlow or SharedFlow: competing collectors distribute packets;
repeated equal ACKs, empty packets and unknown payloads are not conflated or
filtered. The lossless queue is intentionally not described as a bounded total
memory budget. A connection owner must continuously drain it.

Disconnect closes the queue, retains already queued complete packets, and ends
existing and late collectors. Reconnect creates a fresh queue/decoder. Old Flow
handles remain terminal; obtain a new handle after reconnect, or use the
source's higher-layer pattern of constructing a fresh transport. Collector
cancellation alone does not close the physical connection. An owner still must
stop ingestion and disconnect during session teardown; collector cancellation
is not an acknowledgment or permission to reuse an old response.

Swift's receive stream cannot throw and reports receive failures through its
handler/logger. Native Flow additionally terminates with the typed receive,
framing, cancellation or transport failure after draining complete packets.
Clean EOF and explicit disconnect finish normally. This makes an absent
disconnection handler insufficient to hide a failure. WP-107 must handle
exceptional completion in its receive-loop teardown; WP-207 must guard forwarded
callbacks with its connection token. Handlers run outside the state monitor and
must not throw or perform blocking reentrant work.

All eight `WiFiTransportError` cases, associated reasons, value equality and the
eight app error descriptions are retained. `WiFiTransportException.error`
exposes the typed value and preserves the underlying cause. Coroutine stack
recovery may copy ordinary JVM exceptions; assertions verify that the original
cause remains reachable, not an unsupported exception-object identity promise.
WP-304 still owns native localized resources/recovery UI.

The launch base has no WP-106 common `MeshTransportError` implementation. The
mock therefore exposes scoped `MockTransportException.NotConnected` and
`SendFailed(reason)`, preserving both source failure cases and the exact
`"simulated send failure"` reason without creating an unleased shared type.
WP-106/107/217 must deliberately map these cases when assembling common error
and simulator/session consumers; this PR does not claim to port WP-106.

Unlike the source's ignored continuation yield after finish, injection into an
explicitly disconnected mock fails with `NotConnected`. Injection before first
connect remains supported. Mock reconnect preserves successful-send history,
failure threshold and capability configuration. Failure thresholds use Long
(Swift Int width), including source behavior for zero/negative thresholds.

## Blocking IO and platform boundary

JVM sockets are real `java.net.Socket` instances. Only blocking phases run on
the injected IO dispatcher, under `runInterruptible`; calls use structured,
awaited IO jobs. Cancellation/timeout closes the affected socket before
interrupting/joining jobs. Teardown joins registered IO jobs and the owned reader
without awaiting itself. Socket close is attempted once and cleanup failures
are surfaced, including suppressed failure metadata, not swallowed.

A connect mutex serializes the complete attempt and idempotent connect.
A separate write mutex protects the entire framed write, including suspension
and cleanup. Queued operations capture their original generation, so they
cannot write to a replacement connection. Explicit disconnect invalidates
pending pre-disconnect connect requests. Stale completion cannot detach or
notify the new generation.

Default deadlines remain ten seconds for connection and five seconds for a
write. Deterministic tests measure 9,999/10,000 and 4,999/5,000 ms, including
interruptible resolution. The original cancellation test's TEST-NET SYN and
arbitrary delay are replaced by a controlled blocked socket phase with explicit
start/finish barriers and the original three-second completion budget; real
loopback separately proves framing, FIN, RST and
descriptor close.

The default resolver is the JVM/OS resolver. No evidence establishes that
every OS native DNS implementation is interruptible or honors a ten-second
deadline. Cleanup is awaited, so an uninterruptible native resolver can extend
cancellation/timeout completion; this limitation is not concealed by abandoning
a worker or manufacturing connection success. The injected `addressResolver`
and unconnected `socketFactory` permit WP-206's network-scoped, interruptible
resolver/bound sockets without Android dependencies or changing the configured
hostname. Their seams are exercised against a real peer and blocked resolution.
Android LAN permission denial, network binding, `.local` resolution on actual
Android and physical-radio cancellation remain WP-206/device evidence, not
proved by localhost or the APK build.

## Acceptance boundary

See [evidence](../evidence/WP-108/README.md): all 18 assigned Swift test
declarations map to actual passing native cases; 72 transport cases plus all
84 existing primitive cases pass. After reconciling the owning branch with the
actual merged WP-004/104/105 base, the full integrated protocol suite passes
594 cases and the real helper suite passes 35. No original expected packet,
test or fixture was modified; no mandatory case is ignored.

The normal PR is an authorized native implementation, not privileged dispatcher
activation, independent parity approval, human license admission or a physical
radio/signing/release result. Existing GPLv3 app and MIT protocol notices and
strict dependency metadata remain intact. The launchable debug app remains an
intentionally incomplete shell; this package does not wire connected messaging.
